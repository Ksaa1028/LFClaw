# 飞书责任人通知

## 安全边界

- 默认只给通知建议，不自动发送。
- 发送前必须得到用户对接收人、发送身份和最终正文的明确确认。
- 不使用 MaxKB 旧 Python 脚本，不打包应用密钥、tenant token 或通讯录快照。
- 不从静态 JSON 读取人员 `open_id`；每次按飞书当前通讯录解析，避免人员调岗、离职和 ID 过期。
- 未确认具体责任人时禁止发送。
- 同名候选不擅自选择，必须用部门、岗位或用户选择消歧。
- 使用幂等标识防止重试导致重复通知。
- 默认通知协议固定为“总经理助手应用身份 + Card 2.0 交互卡片”，不得自行降级为当前用户或 Markdown/Post。
- 总经理通知只能通过本 Skill 的 `scripts/send-executive-card.mjs` 发送。禁止直接执行 `lark-cli im +messages-send` 或原生消息 POST，避免模型改写身份参数。

## 触发条件

仅在下列情况进入发送流程：

1. 用户明确要求通知、提醒、派发或发送飞书。
2. 用户在看到通知预览后明确确认发送。

重大安全、重大客诉、重大系统故障、重大资金风险只能触发“建议紧急通知”，不能绕过确认直接发送。

## 最小通知原则

1. 普通经营问题只通知离问题最近的唯一直接责任人。
2. 不同时群发责任人、直属上级、协同部门和总经理。
3. 只有逾期、连续恶化、重大安全、重大客诉或重大资金风险时，才建议升级直属上级。
4. 协同部门默认写在消息正文中，不默认抄送。
5. 一次确认对应一次发送；接收人或正文改变后必须重新确认。

## 人员解析

1. 从飞书人力知识库确认责任人的姓名、岗位、部门和直属上级。
2. 使用飞书通讯录能力按姓名搜索当前用户，优先使用用户身份。
3. 单一候选时核对姓名、部门、是否在职和是否跨租户。
4. 多候选时列出姓名、部门和可区分信息，请用户选择。
5. 无候选、已离职或未激活时停止发送并报告原因。
6. 得到 `open_id` 后只把它作为消息工具入参，不在最终答案中展示。

## 发送身份

- 默认且标准身份：总经理助手机器人，以飞书应用身份发送，命令必须显式使用 `--as bot`。
- “总经理助手”显示名称由 LFCLAW 当前 `lark-cli` 所配置的飞书应用决定。Skill 不保存 App ID/App Secret，也不能靠文案伪装机器人名称。
- 发送前检查 bot 身份可用、应用可见范围覆盖接收人，并具备 `im:message:send_as_bot`；私聊还必须已建立机器人与目标用户的可达关系。
- 本 Skill 不提供用户身份发送路径。即使 bot 发送失败，也必须报告失败并停止，绝不静默切换为 `--as user`。

发送预览固定写“发送身份：总经理助手（应用机器人）”。机器人不可达时停止，报告应用权限、可见范围或会话关系问题；如需切换当前用户，必须重新展示预览并单独确认。

## 优先级

只使用以下值：

- 常规关注：轻微异常、普通任务、首次提醒。
- 重点关注：目标明显偏离、需要专项复盘、重要节点临近。
- 紧急跟进：重大安全、重大客诉、重大系统故障、重大资金风险或持续恶化。

优先级决定措辞和处理时限，不自动触发电话、短信或应用内加急。

## 卡片格式

默认使用 Card 2.0 交互卡片，不发送 Markdown/Post。每次构造卡片前必须读取 `lark-im` Skill 的 `references/card/lark-im-card-create.md`，执行其中的组件选型、结构构造与 P0–P7 自检；不得复制固定 JSON 或凭记忆手写卡片。

### 默认视觉基准

以 MaxKB 旧版“总经理智能体事项提醒”卡片为视觉基准，保持正式、简洁、信息密度适中的经营管理风格：

- 使用 `default` 宽度，不使用 `compact`；正文需要舒展展示，不做窄版系统提示卡。
- Header 标题固定为 `总经理智能体事项提醒`，严格按通知严重程度选色：`常规关注=blue`、`重点关注=orange`、`紧急跟进=red`。不得固定使用单一颜色，也不得根据个人审美随意换色。
- Header 不显示 Skill 名称、版本号、Bot 身份标签或测试术语；应用身份由飞书会话顶部自然体现。
- 正文使用白底。禁止把整段正文放进蓝色、紫色等大面积高亮块；颜色只用于 Header、优先级和真正需要强调的少量文字。
- 首屏先展示责任信息：责任人、来源、优先级；存在明确时限时再展示截止时间。字段使用 `div.fields` 或紧凑字段行，保持左对齐。
- 责任信息之后使用一条分隔线，再按 `问题摘要`、`管理动作`、`原始问题` 的顺序分段；章节名加粗，正文使用正常字号。
- `问题摘要` 保留 1–3 段，先写已核实事实，再写需要责任人关注的问题。
- `管理动作` 仅在确有动作要求时展示，写清交付物、验收标准和截止时间；纯提醒不强行增加空栏目。
- `原始问题` 只保留适合直接转发的一句话，不复制冗长对话。
- 默认不放按钮、图片、图表、装饰性图标或彩色标签。只有 LFCLAW 已配置卡片回调处理时才增加操作按钮。
- 卡片底部不写“无需处理”“如显示为机器人即测试通过”等技术说明。

### 内容结构

1. Header：`总经理智能体事项提醒`；常规蓝色、重点橙色、紧急红色。
2. 责任信息：责任人、来源、优先级、可选截止时间。
3. 分隔线。
4. 问题摘要：已核实经营事实与统计口径。
5. 管理动作：责任事项、交付成果、验收标准、协同需求；无实质动作时省略。
6. 原始问题：仅保留适合责任人理解的精简原始诉求。
7. 回执要求：需要闭环时，要求责任人在飞书会话中回复“已确认 + 交付成果 + 截止时间”。

不要把干部测评分数、薪资、合同敏感条款或无关个人信息写入通知正文。

用户原始问题只用于理解上下文。除非原文简短且适合直接转发，否则应提炼为“经营事实 + 责任事项”，不要把整段对话发送给责任人。

## 预览与确认

发送前输出：

```text
【飞书通知预览】
接收人：姓名｜部门｜岗位
发送身份：总经理助手（应用机器人）
消息类型：Card 2.0 交互卡片
优先级：常规关注 / 重点关注 / 紧急跟进
消息正文：
...

尚未发送。请确认是否按以上内容发送。
```

只有用户明确回复确认后才调用飞书消息发送能力。

## 执行与幂等

1. 生成不包含凭证的幂等键，建议由“智能体ID + 接收人ID哈希 + 任务摘要哈希 + 截止时间”组成。
2. 按 `lark-im` 卡片工作流生成并校验 Card 2.0 JSON。
3. 将已确认并通过 P0–P7 校验的 Card 2.0 JSON 写入当前工作目录内的临时文件。
4. 只允许执行 `node <skill目录>/scripts/send-executive-card.mjs --user-id <open_id> --content-file <相对或绝对文件路径>`；群通知将 `--user-id` 换为已确认的 `--chat-id`。脚本内部使用临时请求文件调用飞书消息 API，固定总经理助手 bot 与 interactive 类型，调用者不能覆盖，也不会受到 Windows JSON 引号解析影响。
5. 成功后记录并返回 `message_id`、接收人、发送身份和发送时间。
6. 网络超时但发送状态不明时，不立即重发；先查询或让用户确认是否收到。
7. 明确失败且未创建消息时，修复原因后使用同一幂等键重试。

## 失败处理

- 未找到人员：返回“通讯录未找到”，请用户确认姓名或部门。
- 同名：列候选并等待选择。
- 权限不足：说明缺少用户发送权限、机器人可见范围或应用 scope。
- 机器人不可达：停止发送并说明应用权限、可见范围或私聊关系问题；不得自动改用当前用户身份。
- 超时：标记“发送状态待核实”，禁止直接宣称失败或重复发送。
- 成功：报告“已发送”，附 `message_id`；不输出 `open_id`、token 或请求头。
